PR 135 should make hook files explain themselves.

Codex exposed the bug, but the narrowed fix is simpler: cctop owns the hook binary lifecycle, every session file should record which hook version wrote it, and stale legacy duplicates must not win display identity.

Core invariant: after the app launches, ~/.cctop/bin/cctop-hook should point at the current app-bundled hook. If a session file is still written by something stale, that is a cctop bug we should be able to see immediately, and the reader should not let that legacy file override the canonical record.

--harness remains client identity, not a compatibility check. It tells the hook whether the event came from Claude Code, Codex, opencode, or pi. The debugging addition is hook writer metadata persisted into the session file.

The real failure mode

The scope cut

Product invariant

cctop owns the runtime hook.

The app should keep ~/.cctop/bin/cctop-hook pointing at the current bundled hook. Once the updated app has launched, stale hook writers are not an accepted user state; they are evidence that cctop's own repair path failed.

app-owned symlink repair no rollback support
Client identity

--harness still matters.

The harness value is not a version check. It is the identity channel for clients whose stdin payload cannot be changed, especially Codex and Claude Code shell hooks. opencode and pi send the same identity as JSON harness_name.

cc codex opencode pi

Reduced PR 135 shape

1. Keep

The app-owned hook lifecycle.

The app launch path remains responsible for installing or repairing ~/.cctop/bin/cctop-hook. If that ever leaves the wrong writer in place, debugging should start there.

2. Add

Session writer metadata.

Every session file should include created_by_hook_version and last_written_by_hook_version so a bad file immediately reveals whether an old hook created or later updated it.

3. Dedupe

Canonical Codex files win.

If a numeric PID-keyed, nil-source, no-metadata legacy file shares a session_id with a codex-<session_id>.json file, the reader should group it with the Codex record and display the canonical Codex file.

All clients

The metadata is hook-level, not Codex-only.

Because Claude Code, Codex, opencode, and pi all write through the same cctop-hook, the new fields should appear consistently no matter which client produced the event.

Removed

No capability gate in the shim.

The previous idea of probing hook candidates before dispatch is unnecessary under this product model. If the runtime hook is wrong after app launch, the app-owned repair mechanism is what needs investigation.

Document

Agents inspect writer fields first.

CLAUDE.md and the local agent guidance should tell future agents to inspect hook writer metadata and legacy duplicate shape before changing badge, lifecycle, or grouping logic.

Before vs after

Before

The file did not identify its writer.

When source identity looked wrong, debugging had to infer whether the hook writer, the input payload, or the UI classification logic caused it.

client event -> plugin or shim -> cctop-hook -> session file -> wrong badge / grouping / cleanup -> unclear writer version
After

The file carries writer evidence.

Each session records which hook created it and which hook last updated it. That turns a vague UI symptom into a quick hook-lifecycle check.

client event -> cctop-hook -> session file -> source: client harness -> created_by_hook_version -> last_written_by_hook_version

How to debug the next one

Identity

Client identity survives the hook boundary.

The hook receives a harness identity through JSON harness_name or argv --harness, so HookInput.resolvedHarnessName can set the session source.

correct badge correct file key no legacy fallback
Evidence

Wrong files point to the right layer.

If created_by_hook_version is missing or null, the file was probably created by a pre-metadata hook. If the writer version is current, investigate input resolution or UI classification.

null creator current writer missing metadata
Legacy duplicate

PID-keyed debris cannot beat Codex identity.

A numeric {pid}.json file with no source, no hook metadata, and the same session_id as a codex-<session_id>.json file is old writer output. The Codex-keyed file is the display authority.

same session_id nil source numeric path

Client consistency

Claude Code

Shell shim, argv identity.

The Claude shim passes --harness cc. Its session files should receive the same hook writer metadata as every other client.

Codex

Shell shim, argv identity.

Codex keeps --harness codex as the event identity channel. The new metadata answers which hook binary wrote the resulting file.

opencode / pi

JS/TS plugins, JSON identity.

These clients write harness_name into the payload. Because they still go through cctop-hook, they get the same writer metadata without client-specific fields.

Tests this PR should carry

Session tests

Writer metadata is persisted.

  • New session files include created_by_hook_version.
  • Every update refreshes last_written_by_hook_version.
  • Existing session files without metadata still decode cleanly, but missing created_by_hook_version remains evidence that the original writer is unknown.
  • Metadata is written through the shared hook path, so all clients behave consistently.
Reader tests

Legacy duplicates do not resurface.

  • A source-less numeric PID file and a canonical Codex file with the same session_id collapse to one display record.
  • The Codex-keyed file wins even when the stale PID file has newer activity.
  • The real SessionManager load path publishes only the canonical Codex record.
Docs tests

Debugging guidance is explicit.

  • CLAUDE.md tells agents to inspect writer metadata first when identity looks wrong.
  • Missing or null created_by_hook_version should be treated as likely pre-metadata hook output, not as a normal current-file state.
  • The docs call out numeric PID-keyed Codex duplicates as stale migration debris when a canonical Codex file exists.
  • The guidance distinguishes stale writer evidence from current-writer input or UI bugs.
  • No PR description should imply user rollback or manual executable swapping is a supported scenario.

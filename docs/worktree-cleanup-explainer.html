Worktree Cleanup Explainer

A browser-readable map of how cctop turns ended coding sessions into cleanup candidates, why some rows are clean while others need review, and what has to be true before cctop invokes git worktree remove.

Last updated
2026-06-29 11:18 BST

Current Conclusion

What the feature does It offers a cleanup tab for ended sessions whose project paths resolve to registered linked Git worktrees.
What cctop removes It only asks Git to remove a linked worktree. It does not shell-build a command string and it does not delete folders directly.
What blocks removal Stale preflight state, active sessions, hidden local edits, initialized submodules, identity changes, and changed local-file evidence all refuse before Git removal.
Clean: one confirmation Review: extra warning first Ignored: not actionable Preflight: always re-scan before remove

Problem

Ended coding sessions can leave behind linked Git worktrees that still consume disk space. A cleanup UI has to help the user remove genuinely safe leftovers without accidentally deleting a worktree that has active sessions, unreviewed local files, hidden tracked edits, initialized submodules, or stale identity/evidence.

Root Cause

The hard part is that a worktree's safety can change after it is displayed. Git status can also collapse or hide important evidence. cctop therefore cannot treat a visible row as a durable deletion authorization; it must re-scan and compare current evidence at removal time.

Evidence

Displayed evidence Review rows show reasons and capped local-file previews so users can make a fast decision.
Safety evidence The underlying comparison uses exact source paths, total counts, identity metadata, hidden-index checks, initialized-submodule evidence, and fresh Git inspection.

Solution

The feature separates presentation from authority. The UI presents clean/review candidates and confirmation steps, while the removal service owns the final safety boundary through a fresh preflight scan and strict evidence comparison before invoking Git.

Lifecycle/Data-Flow

Cleanup is derived from session history plus fresh Git inspection. Live sessions protect their worktree; ended sessions can become cleanup candidates.

Session files SessionManager loads current and ended sessions from cctop's persisted state.
Refresh signature Ended-session metadata plus active project paths decide whether a normal refresh should re-scan.
Scanner Ended paths are grouped by resolved worktree root and latest end time.
Git inspector Git worktree metadata, status, commits, index-hidden edits, and submodules become inspection evidence.
Cleanup tab Only actionable clean/review candidates are shown; ignored candidates stay out of the cleanup list.

Scan/Classification Pipeline

Stage Question Clean path Review / ignored path
Path source Is this from an ended session? Latest ended session per resolved worktree root wins. Non-ended sessions do not create cleanup candidates.
Active protection Is a live cctop session using this worktree or a descendant? No active session protects the path. Active or alias-resolved active paths become ignored.
Worktree metadata Is the path listed as a linked Git worktree? Registered linked worktree, with a main checkout path and branch. Missing path, main checkout, unregistered path, detached/unknown branch, or locked metadata needs review or is ignored.
Status evidence Does status show tracked, untracked, or ignored local files? No dirty tracked entries, no untracked files, no ignored files. Tracked edits, untracked files, ignored files, or status failure become review evidence.
Hidden-index evidence Could Git status be hiding a tracked local edit? Assume-unchanged/skip-worktree entries match index contents and mode, or are sparse-checkout index-only paths. Hidden content edits, deletions, mode changes, or symlink target changes become review/refusal evidence.
Commit safety Does the branch have unique local commits? Upstream exists and @{u}..HEAD count is zero. No upstream, unknown branch, or unique commits require review.

Removal Safety Preflight

The Remove button never trusts the displayed row alone. It re-runs candidate generation and compares the fresh candidate with the candidate the user reviewed.

User clicks Remove Only clean/review candidates are actionable. Ignored candidates refuse immediately.
Fresh scan Scanner rebuilds candidates from current sessions and active paths.
Identity/evidence compare Worktree path, main checkout, branch, local-file previews, exact source paths, counts, submodules, and index-hidden evidence are checked.
Git-owned removal Only after checks pass does cctop invoke git -C main worktree remove path.

Refuse before Git

  • Displayed clean candidate becomes review in preflight.
  • Fresh candidate is no longer actionable.
  • Worktree identity changes at the same path.
  • Untracked or ignored evidence changes, including exact whitespace-distinct paths.
  • Initialized submodules or actual index-hidden tracked edits are present.

Let Git decide

  • The candidate is still actionable and its safety evidence matches.
  • Review state is unchanged and does not include unconditional blockers.
  • Git removal can still fail; cctop reports that failure instead of deleting directly.

Clean vs Review Confirmation Flow

Clean detail Shows passed checks and a single Remove action.
Final confirmation Confirms the exact worktree removal before invoking the service.
Review detail Shows review reasons plus local-file previews where available.
Review warning Review candidates require an extra warning step before the final confirmation path.

The UI distinction is about decision quality. The destructive safety boundary remains in WorktreeRemovalService.remove, not in the visual state alone.

Trust/Safety Boundaries For Git Operations

Trusted inputs after verification

  • Git worktree list output for registration and main checkout path.
  • Fresh Git status output with NUL-delimited parsing.
  • Exact raw relative local-file paths for evidence comparison.
  • Git's own refusal behavior from git worktree remove.

Not trusted by itself

  • Stale visible cleanup rows.
  • Collapsed display previews such as cache/.
  • String-only active paths that may be symlink aliases.
  • Clean porcelain status when index flags hide tracked edits.

Candidate generation menubar/CctopMenubar/Services/WorktreeCleanupScanner.swift

Groups ended sessions, protects active paths, classifies clean/review/ignored rows.

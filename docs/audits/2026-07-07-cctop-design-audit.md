# cctop Design-Flaw Audit

Scope: whole repo (Swift app + hook CLI, plugins, scripts, CI). Method: 9 subsystem auditors -> dedup -> adversarial verification of every finding against the code. 63 raw findings, 56 after dedup, **51 confirmed**, 5 refuted. Severity reflects long-term impact on accuracy > maintainability > performance, not current breakage. Verifier corrections are folded in below each finding.


## High severity (2)

### Panel position persistence has five independent writers snapshotting live AppKit geometry, with two conflicting definitions of which screen owns the panel

**accuracy** · confidence high · `menubar/CctopMenubar/Models/PanelPositioning.swift:199`, also: menubar/CctopMenubar/AppDelegate.swift, menubar/CctopMenubar/FloatingPanel.swift

The persisted per-screen panel position (UserDefaults 'panelPositions') is mutated by five uncoordinated paths: drag-end (AppDelegate.swift:654-657), screen-change resave (AppDelegate.swift:459-464), a destructive clear-and-retry when the panel misses the click screen (AppDelegate.swift:566-571), double-click reset (AppDelegate.swift:659-664), and legacy migration (AppDelegate.swift:354-363). Every writer keys the save by an instantaneous read of panel.screen (greatest-overlap semantics, AppDelegate.swift:343-346), while restore validates the saved point by top-left containment ('target.frame.contains(savedPoint)', PanelPositioning.swift:199) — two inconsistent notions of screen ownership. Writes also snapshot panel.frame while the frame can be mid-flight: setFrame(animate:) runs a 0.2s animation (AppDelegate.swift:487-494), show-positioning is deferred via DispatchQueue.main.async (AppDelegate.swift:549-552), and screen changes are debounced 0.5s. There is no single owner of 'where the panel should be'; the live frame doubles as the source for persisting user intent, which FloatingPanel already patches heuristically ('The frame can move under a stationary click… Only a real mouse drag may persist', FloatingPanel.swift:28-34). This is the structural weakness behind the known intermittent panel-drift bug.

**Failure scenario:** A didChangeScreenParameters event (dock resize, display sleep/wake) fires while a custom position exists on screen A but validation fails (e.g. the user last dragged the panel so its top-left corner crossed onto screen B while overlap kept it keyed to A). positionPanel falls back to the anchor on screen B, then resaveAfterScreenChange writes the screen-B frame under screen A's key. From then on every show on A fails containment, snaps to the anchor, and the resave/clear-retry paths keep rewriting or deleting the entry — the user's dragged position silently evaporates or walks a few dozen pixels per toggle, exactly like the observed ~50px/toggle drift.

**Verifier correction:** Three overstatements to trim: (1) the legacy migration is a one-time launch write slated for removal, so there are four live steady-state writers, not five; (2) the "frame mid-flight" concern barely applies to the resave path itself — positionPanel(animate:false) sets the frame synchronously before the read; the mid-flight risk is confined to overlap with in-flight 0.2s resize animations and the isNearlyEqual early-return in setPanelFrame; (3) the causal link to the specific ~50px/toggle drift bug is a plausible hypothesis, not established — the project's paused investigation identified the same fault lines (cross-screen ingredient, clear-retry deleter) but never confirmed the mechanism, and in the described scenario the steady-state symptom is the saved position silently evaporating (anchor fallback each show) rather than continuous per-toggle deletion. The core design claim — no single owner of intended position, live AppKit geometry persisted under two inconsistent screen-ownership definitions, patched by per-path heuristics — stands.

**Direction:** Introduce a single position authority: one component that owns desired-position state, performs all reads/writes of the store, and uses one canonical screen-assignment rule (e.g. always the screen containing the panel's top-left, both at save and restore). Persist only from explicit user gestures (drag-end, reset), never from screen-change or miss-recovery handlers; those should adjust the transient frame only.

### opencode plugin discards per-session identity: all sessions in one process fan into a single fabricated PID session

**accuracy** · confidence high · `plugins/opencode/plugin.js:83`, also: plugins/pi/cctop.ts, menubar/CctopMenubar/Hook/HookHandler.swift

The opencode plugin fabricates one session identity per process (`const sessionId = `opencode-${process.pid}``) and forwards every event it receives into that single identity, ignoring the session ID that opencode attaches to its events (event.properties.sessionID / info.id — the plugin reads info.title at line 151 but never info.id). opencode is a multi-session host: its Task tool spawns child sessions inside the same process, and each child fires session.created, tool.execute.*, and session.idle globally. All of those mutate the one tracked card. The repo already learned this lesson for Codex — files are keyed codex-<session_id>.json precisely because 'one host PID can emit multiple conversations' (HookHandler.swift:657-662) — but the opencode/pi plugin design cannot even distinguish which session an event belongs to, so no downstream keying can fix it.

**Failure scenario:** User runs a Task in opencode; the child session finishes and fires session.idle -> plugin sends Stop -> the card flips to waiting_input while the main agent is still mid-turn. A child session.created resets status to idle and wipes lastTool. A background session's title update overwrites the displayed sessionName (line 151-153). As opencode grows more multi-session features (background agents, server mode), the single card's status becomes an interleaving of unrelated sessions and users stop trusting it.

**Verifier correction:** One overstatement: "no downstream keying can fix it" is true of cctop-hook/the menubar app (identity is discarded before reaching them), but the flaw is locally fixable in the plugin, since opencode events do carry per-session identity (event.properties.sessionID / info.id / info.parentID) that the plugin could filter on or key by. Also the pi half of the claim is weaker: pi's extension already skips non-interactive/background sessions (ctx.hasUI check) and handles session_switch, and pi's single-active-session model makes concurrent same-process interleaving less likely; the strong, verified instance is opencode.

**Direction:** Read the session ID from event payloads and either (a) filter to the primary/root session (ignore events whose sessionID differs from the first session.created), or (b) pass the real session ID through so cctop-hook can key/attribute correctly, mirroring the Codex design. Same applies to plugins/pi/cctop.ts (`pi-${process.pid}`, line 79).


## Medium severity (29)

### Status transitions are memoryless and the hook protocol carries no ordering metadata; event races are patched case-by-case

**accuracy** · confidence high · `menubar/CctopMenubar/Models/HookEvent.swift:46`, also: menubar/CctopMenubar/Hook/HookHandler.swift, menubar/CctopMenubar/Hook/HookInput.swift

Transition.forEvent(_ current:event:) takes the current status but never reads it — the new status depends solely on the event name (HookEvent.swift:46-61). Hook events arrive as independent processes and the code itself documents that they fire concurrently (HookHandler.swift:31-33: 'concurrent hook processes ... race'). The flock in withSessionLock serializes writes but not event order, and HookInput has no timestamp or sequence number, so a late-arriving event legally overwrites a newer status. The design already contains two bespoke patches for discovered instances: notificationPermission is ignored because 'The Notification fires ~6s later and would race with PostToolUse' (HookEvent.swift:56-57), and lastActivity is skipped for that same event to protect a downstream timestamp comparison (HookHandler.swift:111-113). Each new client or event type will keep producing such races, each needing its own hand-tuned exception, because ordering is unrepresentable in the protocol.

**Failure scenario:** At turn end, Claude Code fires the final PostToolUse hook and Stop close together; the OS schedules Stop's process to acquire the lock first. The file ends at 'working' although the agent is waiting for input — the menubar shows a green working card indefinitely, the attention count is wrong, and no waiting-input notification fires until the user manually interacts. The same class of bug recurs with every newly added event (as it already did with permission_prompt) and gets solved with another special case in two switches.

**Verifier correction:** Two narrowing corrections: (1) the inversion is enabled specifically by the plugin's own async:true on tool-use hooks (synchronous events like UserPromptSubmit/Stop/PermissionRequest are serialized by the harness, and opencode/pi plugins use execFileSync), so the racing surface is async tool hooks and delayed Notifications versus other events, not arbitrary pairs; (2) the stuck 'working' card is not truly indefinite — it self-heals on the next user interaction, though the missed waiting-input notification is permanent for that turn.

**Direction:** Add a monotonic event timestamp (or per-session sequence) to HookInput at the shim/plugin layer and make the transition apply-only-if-newer, so ordering is enforced structurally instead of per-event exceptions.

### Session identity and liveness derive from a fragile parent-walk heuristic (hardcoded shell list, depth cap) and are unconditionally overwritten every event

**accuracy** · confidence high · `menubar/CctopMenubar/Hook/HookHandler.swift:222`, also: menubar/CctopMenubar/Models/Session.swift

The session file's primary key (`<pid>.json`, sessionFileName at HookHandler.swift:657-662) and all liveness/cleanup decisions come from getParentPID (HookHandler.swift:222-233), which walks the process tree skipping a hardcoded shell set {sh,bash,zsh,fish,dash} with a fixed depth of 4, assuming the first non-shell ancestor is the harness process. Every event then unconditionally overwrites session.pid/pidStartTime (HookHandler.swift:50-51), so one misfired walk re-keys the session's liveness to the wrong process. The design already carries scar tissue proving the heuristic misfires in the field: the foreign-harness warning log (HookHandler.swift:519-537, 'issue #155 P5') and the comm-name foreign-harness rejection on the read side (Session.swift:645-648) — which is itself another hardcoded string list of harness binary names (Session.swift:634-640). The core contract — 'how the external app spawns hook processes' — is owned by Claude Code/Codex/etc. and can change under cctop at any external release.

**Failure scenario:** Claude Code inserts a non-shell intermediary in hook spawning (a sandbox/router helper, or a shell not in the list such as nushell as the user's SHELL). The walk stops at the short-lived intermediary: each event resolves a different PID, so each event creates a fresh `<pid>.json` with a dead owner — the panel fills with flickering ghost sessions that the next SessionStart's cleanup reaps, live sessions read as stale (isAlive false), and counts/liveness are wrong for every user of that client until cctop ships a heuristic patch.

**Verifier correction:** The risk surface is narrower than claimed: only the Claude Code path combines the parent walk with PID keying. opencode and pi spawn cctop-hook directly via execFileSync (the walk is a no-op landing on the correct harness PID), and Codex both execs the hook from its shim and keys files by session_id (codex-<sid>.json), so a walk misfire cannot fragment Codex sessions. The nushell-as-$SHELL trigger is wrong — run-hook.sh has a pinned #!/bin/sh shebang, so the failure requires Claude Code itself to interpose a non-shell intermediary. The "unconditional overwrite" at HookHandler.swift:50-51 is consistent-by-construction for PID-keyed files (the written pid always equals the filename key) and only produces drift for Codex files. Read-side mitigations (pidStartTime check, foreign-comm rejection, SessionStart cleanup, session-id-keyed SessionEnd) bound the failure to transient ghost sessions rather than permanent corruption. Severity stays medium because Claude Code is the primary harness and the failure mode (per-event ghost files until a heuristic patch ships) is real, but the claim overstates it as affecting session identity for every harness.

**Direction:** Have each integration pass the harness PID explicitly (plugins already know process.pid; the CC/Codex shims can pass $PPID via --flag), keeping the parent walk only as a legacy fallback, so identity stops depending on reverse-engineering external spawn trees.

### Derived display lifecycle stored inside the persisted model with an implicit assign-after-load contract defaulting to .active

**accuracy** · confidence high · `menubar/CctopMenubar/Models/Session.swift:245`, also: menubar/CctopMenubar/Models/SessionDisplayPolicy.swift, menubar/CctopMenubar/Models/StatusCounts.swift, menubar/CctopMenubar/Services/SessionManager+Archive.swift, menubar/CctopMenubar/Services/SessionManager+Notifications.swift

`lifecycle` is a stored `var` on the persisted `Session` struct, excluded from CodingKeys so every decode silently defaults it to `.active`; the real value is mutated in after load by one code path (SessionManager+Archive's candidate builder). Everything downstream — SessionDisplayPolicy filters, StatusCounts (the menubar badge), notification gating, dormant card dimming, and Session.sorted — trusts the field without any way to know whether derivation ran. The type system cannot distinguish a raw decoded session from a lifecycle-decorated one, and the failure direction is the worst one: forgotten derivation makes finished/dormant sessions look active.

**Failure scenario:** A new feature reads sessions outside the blessed load path — e.g. a widget, CLI query, or a quick fix that calls Session.fromFile / decodedSessions and passes results straight to StatusCounts or Session.sorted. Every dormant and finished session decodes as `.active`, so the menubar badge counts dead sessions as live work, notifications fire for sessions whose process exited days ago, and sorting interleaves finished sessions with live ones. Nothing crashes and no test of the main path catches it.

**Verifier correction:** The claim is correct except for the framing that "the failure direction is the worst one": a defaulted .active is the worst direction for silent display accuracy (badge counts, notifications, sorting) but the fail-safe direction against data loss — nothing deletes or archives based on .active, and GC only removes files on a locally re-derived .finished. Also, derivation discipline exists in more than one place: three non-display paths already re-derive lifecycle after fromFile rather than trusting the field, showing the contract is known but enforced only by convention.

**Direction:** Move the derived state out of the persisted struct: a small `DisplaySession` (or `(session, lifecycle)` value) produced only by SessionLifecyclePolicy, and make SessionDisplayPolicy/StatusCounts/sorted accept that type so an undecorated Session cannot reach lifecycle-dependent APIs.

### waiting_permission display heuristic (any new child process) also drives the notification state machine, silently cancelling attention alerts

**accuracy** · confidence high · `menubar/CctopMenubar/Services/SessionManager.swift:344`, also: menubar/CctopMenubar/Services/SessionManager+Notifications.swift

adjustPermissionStatus flips a persisted waiting_permission status to working whenever the harness process has any direct child whose kernel start time is newer than the file's lastActivity (wall-clock comparison with a 1s tolerance). This display adjustment is applied to newSessions before syncTransitionNotifications runs, so notificationActions treats the session as no-longer-needsAttention and removes the pending and delivered permission notification. The heuristic conflates 'a child process appeared' with 'the user granted permission', which becomes less true as harnesses spawn more background children (MCP servers restarting, file watchers, backgrounded shells, parallel tool calls), and it couples a cosmetic presentation tweak to the app's primary attention signal.

**Failure scenario:** A session hits PermissionRequest and the user walks away. An MCP server the session runs spawns a helper process (or restarts) after the request. On the next 2s pass the card renders 'working', and the already-delivered permission notification is deleted from Notification Center — the one persistent cue the user had. The session sits blocked on a permission prompt indefinitely while cctop reports it as working, directly inverting the app's core promise.

**Verifier correction:** The heuristic only inspects direct children of the harness PID, so the "MCP server spawns a helper" vector is impossible; and because the on-disk status remains waiting_permission, a short-lived spurious child causes notification remove-then-repost churn on the next 2s poll rather than permanent loss. The genuine long-term risk is narrower: any long-lived direct child the harness spawns after PermissionRequest (restarted MCP server, auto-updater, watchdog) permanently renders the blocked session as "working" and deletes the delivered notification with no self-correction, and this coupling of a display heuristic to the attention/notification state machine is untested and undocumented.

**Direction:** Separate the two consumers: feed notifications from the persisted status (or only remove notifications on an authoritative hook transition), and keep the child-process inference as a display-only hint — or replace the inference entirely with a hook event when permission is granted.

### History pruning enforces one file per project while Recent Projects counts files per project, structurally pinning the displayed session count to 1

**accuracy** · confidence high · `menubar/CctopMenubar/Services/HistoryManager.swift:230`, also: menubar/CctopMenubar/Models/RecentProject.swift

Two invariants about the same directory contradict each other inside one file. buildRecentProjects aggregates `count: existing.count + 1` per project and surfaces it as RecentProject.sessionCount, rendered in the card metadata as 'N sessions'. But filesToPrune removes every history file after the most recent one per canonical project path (`seenProjects.contains(canonicalPath)` → toRemove), and pruneHistory runs after every single archive. So at steady state each project has exactly one history file and the UI perpetually reads '1 session' regardless of real usage; the counting code is dead weight that misleads. The mock data (sessionCount 12, 5, 8) shows the design intent was a real count.

**Failure scenario:** A user runs dozens of sessions in a project over a month; the Recent Projects card always says '1 session', quietly wrong forever. Worse, the contradiction traps future maintainers: whoever 'fixes' the count by relaxing the one-per-project prune multiplies the history-dir size that the every-2s rebuild decodes (see the rebuild-cost finding), while whoever tightens pruning further doesn't realize they are also editing what the UI number means.

**Verifier correction:** Minor refinement only: there is no user-visible transient window where the count exceeds 1, because archiveSession's write and prune are one synchronous @MainActor operation that cannot interleave with rebuildRecentProjects; the count is pinned to 1 absent prune-deletion failures. The finder's maintenance-trap framing is otherwise accurate, including that relaxing the prune to fix the count would grow the per-rebuild decode cost, and that the existing unit tests assert count aggregation behavior (3, 2) that production can never exhibit.

**Direction:** Pick one source of truth: either store a running per-project session counter in the single retained history file (increment on archive) or stop displaying a count. Do not derive the count from a file population that pruning deliberately collapses.

### Codex schema drift degrades to silent wrong answers: pinned state_5.sqlite filename plus column-fallback SQL

**accuracy** · confidence high · `menubar/CctopMenubar/Services/CodexThreadArchiveLookup.swift:162`, also: menubar/CctopMenubar/Models/Config.swift, menubar/CctopMenubar/Services/SessionManager+Archive.swift

The lookup couples to two Codex-internal version knobs with no detection when they move. (1) The database filename hardcodes Codex's internal schema generation: Config.swift:20 `codexStateDatabaseFilename = "state_5.sqlite"` — the '5' proves Codex bumps this on migrations. When state_6.sqlite ships, every candidate path misses and the snapshot becomes .missing, which archivedThreadIDs/subagentThreadIDs/execHelperThreadIDs deliberately map to [] (CodexThreadArchiveLookup.swift:71-73, 84-86, 110-113). (2) Within the file, threadSnapshotSQL substitutes constants for missing/renamed columns: `selectColumn` emits `0 AS archived` / `NULL AS thread_source` (lines 125-134, 162-164), so a column rename reads as 'nothing archived, nothing subagent' for all rows. Neither path logs or surfaces that the store went dark.

**Failure scenario:** Codex releases a migration to state_6.sqlite (or renames `archived` to `archived_at`). Overnight, every archived Codex Desktop thread reappears in the menubar as a live session, subagent and exec-helper threads stop being hidden, and the 45s GC (`isCodexDesktopThreadArchived` sees [] => not archived, SessionManager+Archive.swift:572-581) starts deleting .json files for threads the user archived and may later unarchive — all silently, with no log line distinguishing 'no Codex installed' from 'schema moved'.

**Verifier correction:** The claim is mechanically correct but overstates harm and misses the likelier failure mode. If a Codex migration leaves state_5.sqlite behind (common), cctop silently serves stale answers from the old DB rather than hitting .missing => []; both modes are silent and wrong. The GC deletion destroys only cctop's own session records (recreated on the next hook event from that thread) — Codex-side rollouts/DB and in-Codex unarchive are unaffected, so there is no user data loss, only loss of cctop's archived-resumable entries and panel accuracy (archived threads reappearing, subagent/exec helpers unhidden). The genuine design flaw is that schema drift degrades to plausible-but-wrong answers instead of a detectable "unknown" state: no log line, glob check (state_*.sqlite with a newer generation), or tripwire distinguishes "Codex not installed" from "schema generation moved". Severity medium: certain to trigger eventually (the filename is literally versioned at 5) and silent, but recoverable and confined to display/metadata.

**Direction:** Probe for the newest state_N.sqlite by glob instead of pinning N=5; when the pinned/expected schema is absent but a newer generation exists (or expected columns are missing), log loudly and treat archive state as unknown (nil / fail-open-keep) rather than empty, so GC never deletes on a schema mismatch.

### Codex Desktop DB discovery fingerprints another app's private CLI flags and requires exactly-one topology

**accuracy** · confidence high · `menubar/CctopMenubar/Services/CodexDesktopRuntimeProbe.swift:56`, also: menubar/CctopMenubar/Models/Config.swift, menubar/CctopMenubar/Services/CodexThreadArchiveLookup.swift

currentDesktopSQLiteHome identifies the Desktop-owned app-server by matching Codex's private, undocumented process invocation: the exact flag `--analytics-default-enabled`, the absence of `--listen`/`stdio://`, and a bundle-path prefix (lines 56-65). It additionally demands exactly one running Codex Desktop app AND exactly one matching child (`apps.count == 1`, `servers.count == 1`, lines 47-51), returning nil otherwise. nil silently falls back to config.toml / ~/.codex defaults (Config.codexStateDatabaseCandidates), which typically point at the CLI's database — a different store than the Desktop's CODEX_SQLITE_HOME. There is no positive verification that the fallback DB is the one Desktop is actually writing, and no signal that discovery failed.

**Failure scenario:** Codex ships an update that drops or renames --analytics-default-enabled, or starts running two app-server children (e.g. one per workspace window). Discovery returns nil forever after; cctop reads archive/subagent state from the CLI database instead of the Desktop one, so archiving a thread in Codex Desktop no longer hides it in cctop (or worse, threads get classified from a stale sandbox DB) — a silent accuracy regression with no log to diagnose.

**Verifier correction:** Not an exclusive fallback: Config.codexStateDatabaseCandidates (Config.swift:75-95) prepends the probed desktop home to a candidate list that always includes config.toml/~/.codex paths, and CodexThreadArchiveLookup queries all candidates and merges — so probe failure loses only the Desktop-specific candidate rather than switching stores. The regression is silent and permanent only for the flag-drop scenario; the two-apps/two-servers case self-heals once topology returns to one (1s path cache). Impact is limited to users whose Desktop CODEX_SQLITE_HOME is not among static candidates, which is the population the probe exists to serve.

**Direction:** Anchor on the stable signal (any bundled child exposing CODEX_SQLITE_HOME in its environment) instead of the flag set; accept multiple candidates by unioning their sqlite homes into the candidate list rather than bailing on count != 1; log when the probe finds Codex Desktop running but cannot resolve a home.

### Notch pill visibility mixes cached and live screen state and compares coordinates across different displays

**accuracy** · confidence high · `menubar/CctopMenubar/AppDelegate.swift:288`, also: menubar/CctopMenubar/Services/NotchStatusController.swift

The pill decision consumes a mixture of state snapshots taken at different times: `hasNotch` is cached at launch (AppDelegate.swift:67) and refreshed only inside the 0.5s-debounced screen-change work item (line 449), while resolveVisibility simultaneously takes the cached `hasNotch` and a live `NSScreen.builtin != nil` read (lines 308-314; NotchStatusController.swift:89-101) — two answers to the same question that can disagree during display transitions. isStatusItemOccluded (lines 288-297) compares `statusItem.button.window.frame.minX` against `NSScreen.builtin.frame.maxX - auxiliaryTopRightArea.width` without checking that the status-item window is actually on the built-in display, so on layouts where an external display owns the menu bar the comparison mixes global coordinates from two different screens. The whole path is stitched together with ad-hoc debounces (0.25s notch work at lines 327-329, 0.5s screen work at line 467) and cross-cutting cancels (line 542), so each new trigger source needs to know about every timer.

**Failure scenario:** A MacBook with the built-in display arranged to the right of an external main display (built-in global minX ≈ 2000): the status-item window sits in the external display's menu bar at minX ≈ 1400, which is less than the built-in screen's visibleMinX ≈ 3300, so the icon reads as occluded and the pill appears next to the notch even though the menubar icon is fully visible — or during clamshell open, the stale cached hasNotch tears the pill down for half a second and re-creates it, flickering user-visible status.

**Verifier correction:** The core finding stands, but the clamshell sub-claim is overstated: during clamshell the pill is already torn down (live hasBuiltinScreen=false forces tearDown), so on lid open the stale cached hasNotch=false causes only a ~0.5-0.75s delay before the pill can appear — an appearance delay, not a user-visible tear-down/re-create flicker. The substantive defects are (1) isStatusItemOccluded comparing a window frame from an unchecked display against built-in-screen coordinates (persistent false positives/negatives whenever the external display hosts the status-item window), and (2) three separately-timed reads of built-in-screen state feeding one decision, stitched by debounces and cross-cutting cancels.

**Direction:** Derive a single ScreenConfiguration snapshot (built-in screen, notch, status-window screen and frame) at one point per change and pass it through resolveVisibility; require the status-item window's own screen for the occlusion comparison; remove the cached hasNotch in favor of reading from the snapshot.

### Confirm-to-delete TOCTOU guard compares path shapes, not content: force removal deletes work written while the confirmation dialog was open

**accuracy** · confidence high · `menubar/CctopMenubar/Services/WorktreeRemovalService.swift:258`, also: menubar/CctopMenubar/Models/WorktreeCleanupCandidate.swift, menubar/CctopMenubar/Views/PopupView+Cleanup.swift, menubar/CctopMenubar/Services/WorktreeCleanupScanner.swift

The removal flow correctly re-scans between confirmation and execution (executeConfirmed -> selectedAction -> fresh inspectGit) and refuses when evidence changed. But `matchesConfirmedRemovalEvidence` defines 'unchanged' as: same worktree/branch identity, same reason set, same untracked/ignored path sets, and same trackedPathSignature — all path-name signatures. No content fingerprint (blob hash, mtime, size) of the dirty files is captured, and the confirmation Alert can sit open indefinitely. So the design detects a NEW dirty file or a new commit (the interpolated 'Branch has N unique local commits' string changes), but is structurally blind to mutations of files already listed — exactly the files a force removal will destroy. In cctop's own domain (agents and build tools writing into worktrees unattended, some not tracked by cctop sessions), 'same file path, new content' is the common case, and the guard architecture gives a false sense that it is covered.

**Failure scenario:** User clicks Remove on a worktree with 'Untracked files: notes.md' and leaves the Force Remove confirmation open. A build script, editor autosave, or an untracked agent process writes an hour of output into notes.md (same path). User returns and clicks Force Remove: the fresh preflight produces an identical path-set signature, matchesConfirmedRemovalEvidence passes, and `git worktree remove --force` deletes the new content. The user consented to deleting the old notes.md, not the new one — and this is the only subsystem that deletes user data.

**Verifier correction:** Mostly correct, with one overstatement: the in-domain "unattended agent writing into the worktree" case is partially mitigated, because a cctop-tracked session becoming active at that path causes executeConfirmed to refuse via the activeProjectPaths preflight (tested at WorktreeCleanupTests.swift:3196), and new commits change the interpolated reason string and are also refused. The real blind spot is narrower: content mutation of already-listed dirty files by writers cctop does not track (build scripts, editor autosave, watch daemons, non-hooked agents) during the unbounded confirmation window. Severity stays medium because this is the only data-deleting subsystem and the guard's precision elsewhere implies coverage it does not have.

**Direction:** Include a content dimension in the confirmed evidence: e.g. hash the `git status` raw output plus per-dirty-file (size, mtime) or `git hash-object` of listed paths at confirmation time, and/or expire confirmations after a short TTL so a stale dialog forces a fresh review.

### Hand-rolled TOML flag reader recognizes only one spelling of [features].hooks despite a real TOML parser being available

**accuracy** · confidence high · `menubar/CctopMenubar/Services/CodexConfigToml.swift:79`, also: menubar/CctopMenubar/Services/CodexPluginInstaller.swift, menubar/CctopMenubar/Models/Config.swift, menubar/CctopMenubar/Services/PluginManager.swift

isHooksEnabled() drives the user-visible installed/hooksDisabled distinction (CodexPluginInstaller.isInstalled -> PluginManager.codexHookStatus), but it is a line scanner that only understands the `[features]`-table-header spelling. TOML allows the same setting as a root-level dotted key (`features.hooks = false`) or an inline table (`features = { hooks = false }`); Codex, parsing real TOML, honors those, while cctop's scanner skips them (scan() at lines 107-139 attributes keys only when `current == "features"` after a `[features]` header). The project already links TOMLDecoder and uses it for config reads (Config.swift:159-165 decodes sqlite_home from the same file), so the read path is duplicated between a real parser and a weaker hand parser. Hand-rolled scanning is defensible for minimal *patching*, but using it for *detection* means cctop's answer to 'will hooks fire?' can disagree with Codex's.

**Direction:** Treat the marker list as a shared source of truth: derive it from the harness registry (one declared worktree-layout hint per supported client) or persist the worktree root evidence in the session file at hook time (the hook can run git freely in the session's own cwd), so the app does not have to guess external tools' directory layouts after the fact.

### Log lifecycle: per-event appends with no rotation, per-session logs orphaned on the common clean-exit path, and _errors.log fully re-read for dedup

**performance** · confidence high · `menubar/CctopMenubar/Hook/HookLogger.swift:44`, also: menubar/CctopMenubar/Hook/HookHandler.swift

HookLogger appends one line per hook event to ~/.cctop/logs/<session_id>.log with no size cap or rotation (HookLogger.swift:37-45, 61-76) — including a line for every PreToolUse/PostToolUse ('working -> working' noise). Log deletion exists only on the hook-side stale-cleanup path (removeSession, HookHandler.swift:499-512). The common lifecycle — SessionEnd stamps ended_at (HookHandler.swift:380-419) and the app later archives and removes the JSON only ('SessionManager archive/GC paths remove session JSON only', AGENTS.md) — never deletes the log, so every cleanly-ended session leaks its log file forever. _errors.log is also append-only forever, and logSessionLoadFailureOnce reads the entire file into memory to substring-search a marker on every load failure (HookHandler.swift:629-639), so the dedup check itself gets slower as the unrotated log grows.

**Failure scenario:** After months of daily use, ~/.cctop/logs accumulates thousands of orphaned per-session logs (one per ended session, each with a line per tool call) totaling hundreds of MB, and a user who once had a recurring hook error has a multi-MB _errors.log that every subsequent load-failure path re-reads in full. Disk growth is silent because nothing in the app surfaces or manages the logs directory.

**Verifier correction:** Substantially correct; two calibrations. (1) Scale: the heaviest-use machine available (the developer's) shows 36MB/1352 files, so "hundreds of MB" is a multi-year extrapolation rather than a typical months-of-use outcome — growth is real, unbounded, and silent, but slow. (2) The _errors.log full re-read in logSessionLoadFailureOnce runs only on the rare session-load-failure path (corrupt/undecodable session file), so its per-event cost (a few ms to read a multi-MB file, repeated per hook event while a corrupt file persists) is a minor secondary issue, not a hot path. Low severity is appropriate.

**Direction:** Give one side clear ownership of log GC (e.g., the app's slow GC pass deletes logs for archived/removed sessions and trims _errors.log), and replace the full-file dedup read with a small marker file or tail-bounded check.

### Degraded-format path pins full file contents in memory and rescans them by substring on every snapshot

**performance** · confidence high · `menubar/CctopMenubar/Services/ClaudeDesktopSessionArchiveLookup.swift:124`

When a metadata file contains a cliSessionId key but the typed decode or hand-rolled scanner cannot fully parse it, the ENTIRE file content is appended to uncertainContents and retained inside the cached index (lines 124-131, 151-155). Every snapshot(matching:) call — every 2-second pass — then runs `content.contains(sessionID)` over all uncertain contents times all queried session IDs (lines 247-250). This is exactly the path that activates when Claude Desktop evolves its schema (e.g. cliSessionId becomes nested or non-string), so the design's response to upstream drift is to hold the whole store's bytes in memory and do O(files x sessionIDs x fileSize) substring searches per pass, while also nil-ing the snapshot and disabling classification.

**Failure scenario:** A Claude Desktop update changes the metadata shape so JSONDecoder fails on every file but the raw key string remains present. cctop's resident memory grows by the size of the entire claude-code-sessions store (hundreds of MB), and each 2-second pass performs full-text substring scans of that corpus against every Claude Desktop session ID — degradation that looks like a cctop memory/CPU leak rather than an upstream format change.

**Verifier correction:** If Claude Desktop changes cliSessionId to a non-string/nested value (or adds any nested cliSessionId occurrence with a non-string value — even in files whose typed decode still succeeds), each affected file's full content is pinned in the cached index and substring-scanned against every tracked Claude Desktop session ID on each 2s pass. Realistic impact is holding and rescanning single-digit MB of metadata (measured store: 6.6 MB / 62 files), growing with unpruned conversation count, and only while Claude Desktop sessions are tracked — a modest, bounded degradation, not a hundreds-of-MB leak. Plain JSONDecoder failures do not trigger content pinning.

**Direction:** Store only the extracted candidate session-ID strings (or a bounded excerpt/hash) for uncertain files instead of full contents, precompute the uncertain-ID set once at index build, and log a distinct 'metadata format unreadable' signal so schema drift is diagnosable.

### Session updates force a synchronous full SwiftUI layout pass on the main thread for every publish while the panel is visible

**performance** · confidence high · `menubar/CctopMenubar/AppDelegate.swift:226`, also: menubar/CctopMenubar/Services/SessionManager.swift, menubar/CctopMenubar/Views/PopupView.swift

observeSessionUpdates schedules resizePanel(animate: true) on every $sessions emission while the panel is visible (AppDelegate.swift:226-230), and resizePanel calls panelFittingSize() which forces `panel.contentView?.layout()` plus NSHostingView.fittingSize — a synchronous measurement of the entire SwiftUI hierarchy (AppDelegate.swift:479-483). Sessions republish whenever any field changes (Session equality includes lastActivity/last_tool, SessionManager.swift:104-110), so with N busy agents each tool event triggers a publish, throttled only by the 0.1s watcher debounce (SessionManager.swift:421-427) plus a 2s liveness timer. The 'when to resize' decision has no owner: the SwiftUI side also independently requests resizes via onLayoutChanged (PopupView.swift:406-408), so AppDelegate brute-forces a layout pass on every data tick as a catch-all, even when only a timestamp changed and the frame guard (isNearlyEqual, line 486) will discard the result.

**Failure scenario:** A user keeps the panel open while 6-8 agents run tools concurrently; session files churn at the debounce ceiling (~10 publishes/sec), each forcing layout()+fittingSize over a card list that keeps growing richer (agent badges, cleanup rows, banners). The panel becomes visibly janky and the app burns main-thread CPU exactly when the user is watching, and every new card feature makes the per-tick layout pass more expensive.

**Verifier correction:** The 'no single owner of resize decisions' observation is valid: the data sink brute-forces a synchronous layout()+fittingSize measurement on every session publish while the panel is visible, even when only lastActivity/lastTool changed and the frame guard then discards the result, and PopupView independently requests resizes via onLayoutChanged. But the throttle is a trailing 0.1s debounce (sustained churn delays publishes rather than sustaining ~10/sec), publishes only occur when data actually changed (so a SwiftUI render was due regardless), and the measured content is a LazyVStack capped at 600pt — so the redundant per-tick cost is low-millisecond, making this a design-cleanliness/scalability concern rather than a present or near-term jank risk. Severity: low.

**Direction:** Make content-size change the trigger, not data change: rely solely on the SwiftUI-side onLayoutChanged callback (or a GeometryReader/preference reporting intrinsic height) and drop the resize-on-every-publish sink, or gate it on a cheap derived signature (session count/bucket) rather than full publishes.


## Refuted findings (for the record)

- **Session file round-trip drops fields written by a newer binary (no unknown-key preservation or version write-guard)** (menubar/CctopMenubar/Hook/HookHandler.swift) — The Codable mechanics are correctly described (unknown keys dropped, whole-file rewrite, version stamps never compared), but the failure scenario's premise is wrong: ~/.cctop/bin/cctop-hook is a symlink into the app bundle (AppDelegate.swift:668-684), exec'd fresh per event by run-hook.sh, so a Sparkle in-place bundle swap makes the very next hook event run the NEW binary — app and hook version-flip atomically and no "stale hook until app relaunch" window exists in production. Version skew is confined to dev workflows, which AGENTS.md explicitly documents and mitigates (line 29 "do not leave ~/.cctop/bin/cctop-hook stale", line 22 schema changes must update install tooling in the same change), and there is no third writer of session JSON.

- **Path-cache TTL (1s) shorter than the poll cadence (2s) makes the process-tree/TOML probe run on every pass on the main thread** (menubar/CctopMenubar/Services/CodexThreadArchiveLookup.swift) — The cited code and numbers are real, but the claim misreads intent: SessionManager+Archive.swift:20-22 documents the 1s cache as a "short internal cache for repeated reads in one pass" — it deliberately coalesces the ~5 lookup calls per loadSessions pass into one probe, and fresh per-pass resolution is required because the resolved DB path feeds hide/GC-delete classification that must notice a Codex Desktop restart (CODEX_SQLITE_HOME change) promptly. The failure scenario is implausible in magnitude: the probe only runs when Codex thread IDs exist, skips the child scan when Desktop isn't running, and costs well under a millisecond per 2s pass (direct children only, bounded sysctl reads, small TOML), which is marginal next to the JSON decoding and SQLite fingerprinting loadSessions already does synchronously on the main actor.

- **Session-resume deep links mirror an external app's private, unversioned URL contract with no capability detection** (menubar/CctopMenubar/Models/HostApp.swift) — The cited code is real, but the claim misreads it and proposes infeasible mitigations: macOS has no API to capability-detect or version a third-party private URL scheme, so tested graceful degradation (FocusStrategyTests.swift:337-346) is the correct available design; the ignored NSWorkspace.open Bool could not surface the claimed drift anyway (LaunchServices returns true once any handler accepts the scheme, and in the isUUID-rejection path no URL is ever opened); and isUUID doubles as interpolation sanitization consistent with the file's other guards. The fork-vs-focus rationale is not comment-only — it is pinned by testClaudeDesktopUsesActivateByBundleID (which a contributor wiring claude://resume would break) and recorded in AGENTS.md's harness table (lines 215/217), making the trade-off documented and deliberate.

- **Every panel open performs synchronous multi-integration file IO on the main thread before the panel appears** (menubar/CctopMenubar/AppDelegate.swift) — The code facts are accurate: AppDelegate.swift:545 calls the @MainActor pluginManager.refresh() before makeKeyAndOrderFront, and PluginManager.swift:56-92 does per-integration stats, a cache-directory scan, a full read of ~/.codex/config.toml, and bundled-vs-installed byte comparisons. But I measured the exact IO pattern against the user's real home directory with all four integrations installed (config.toml 8.7KB, plugin.js 5.9KB, hooks.json 1.5KB): ~2.2ms on a cold-ish first run, ~0.07ms warm — roughly 0.5ms per integration at worst. The projected failure ("two or three more integrations → perceptible stall") needs ~50+ integrations or a networked home directory to reach the ~100ms perceptibility threshold, which is implausible for a menubar app whose realistic integration count is single-digit and whose developer audience runs local APFS homes. The inline comment (AppDelegate.swift:543-544) also documents re-read-on-every-open as a deliberate freshness decision — Codex hook trust changes outside the app — and an async refresh would trade microseconds for flash-of-stale-state in the panel UI.

- **Dead injection seam resolveLinkedWorktreeRoot is wired in production and stubbed in a dozen tests but never called** (menubar/CctopMenubar/Services/WorktreeCleanupScanner.swift) — The factual kernel is confirmed (grep shows resolveLinkedWorktreeRoot is wired in live() at WorktreeCleanupScanner.swift:52 but invoked nowhere in production, and GitWorktreeInspector.linkedWorktreeRoot has no production caller), but the finder misread the tests: all ~12 stubs are spies that assert the closure is NEVER called (XCTAssertEqual(linkedRootPaths, []) at WorktreeCleanupTests.swift:182/261/344/403/457, linkedRootCount == 0 at 1891/1943/1988/2033, and XCTFail("Protected cleanup action should not resolve linked roots") at 2882), so they cannot give "false confidence that linked-root resolution participates in candidate/protection logic" — they document the exact opposite, and each XCTFail message explains why. The introducing commit 89b60179 (#206) explicitly records the deferral ("Defer hidden linked worktree probes"), so the seam is a deliberately parked probe with negative-contract regression guards, not an unexplainable dead injection point; both halves of the failure scenario (prod/test divergence from stubbing an uncalled closure, and a "wall of stubs nobody can explain") are implausible against this code.
